# AGENTS.md — job_aggregator

Система мониторит Telegram-каналы (позже сайты), извлекает вакансии/подработки, нормализует, дедуплицирует, фильтрует, оценивает релевантность и риск, сохраняет в PostgreSQL и шлёт подходящие в личный Telegram через бота.

Этот файл — постоянные правила. Задачи приходят отдельными промптами. Если задача противоречит этому файлу, остановись и укажи на противоречие, а не молча выбирай.

## Принципы (в порядке приоритета)

1. Надёжность и корректность данных.
2. Идемпотентность.
3. Расширяемость (новые источники без правки ядра).
4. Объяснимость: каждое решение имеет машиночитаемые коды причин.
5. Простота. Не добавлять технологию без письменного обоснования в `docs/decisions.md`.

## Стек

Python 3.11+, aiogram 3.x, Telethon (только мониторинг Telegram), asyncio, PostgreSQL, SQLAlchemy 2.x (async), Alembic, Pydantic 2.x, httpx, APScheduler, pytest, Docker Compose. Playwright только если источнику реально нужен JS.

**Redis не использовать** до Phase 4. Очередь задач и очередь уведомлений живут в PostgreSQL (`SELECT ... FOR UPDATE SKIP LOCKED`). Переменной `REDIS_URL` в `.env.example` быть не должно.

## Границы ответственности

- **Bot** (aiogram): команды, настройки, управление источниками, показ уведомлений. Не парсит.
- **Scheduler**: только создаёт задачи (live / initial_sync / backfill). Не парсит.
- **Worker**: fetch → pipeline → запись результатов → постановка уведомлений.
- **Notifier**: единственный компонент, который шлёт сообщения пользователю. Parser-воркеры не шлют ничего напрямую.
- **PostgreSQL**: единственное хранилище и единственная очередь.

На MVP всё может жить в одном процессе, но модули не должны импортировать друг друга в обход этих границ.

## Pipeline (порядок обязателен)

```
FETCH → PARSE → NORMALIZE → VALIDATE
→ PERSIST RAW (vacancy + vacancy_sources, идемпотентно)
→ DEDUPLICATE
→ TEXT HARD REJECTS (дешёвые правила по нормализованному тексту)
→ STRUCTURAL EXTRACTION (remote/office, график, зарплата, опыт, звонки, командировки…)
→ STRUCTURAL HARD REJECTS (правила, зависящие от extraction)
→ RELEVANCE SCORING
→ RISK ENGINE
→ PERSIST EVALUATION
→ NOTIFICATION DECISION → NOTIFICATION QUEUE → SEND
```

Вакансия сохраняется сразу после validate. Падение воркера не должно приводить к потере вакансии. Отклонённые и дубликаты не удаляются никогда.

## Статусы — три независимые оси, не один enum

- `vacancies.ingest_status`: NEW, PARSED, INVALID, DUPLICATE
- `vacancy_evaluations.decision`: PENDING, HARD_REJECTED, FILTERED, APPROVED (на пару vacancy × user)
- `notifications.status`: QUEUED, SENDING, SENT, FAILED, SKIPPED

Переходы описаны явно (таблица допустимых переходов в коде) и покрыты тестами. Недопустимый переход бросает исключение.

## Пользователи и оценки

Сейчас один пользователь, но схема multi-user-ready:
- `risk_score`, `risk_level`, `risk_flags` — свойства вакансии.
- `relevance_score`, `decision`, причины фильтрации — свойства пары (vacancy, user) в `vacancy_evaluations`.
- Не класть relevance_score в `vacancies`.

## Правила фильтрации

Три типа, не смешивать: **Hard Reject** (абсолютный, score не отменяет), **Soft Penalty**, **Positive Signal**. Правило hard reject не может быть автоматически понижено до soft.

Правила живут в конфиге/БД, не в коде. Дефолты — `config/default_rules.yaml` (seed). Веса скоринга — в конфиге, формула документирована в `docs/scoring.md`. Решение об отправке: `relevance_score >= minimum_relevance_score` И `risk_level <= maximum_risk_level`.

**Негации обязательны.** «без холодных звонков», «звонки не нужны», «не требуется опыт» — не то же самое, что «холодные звонки», «нужен опыт». Матчер учитывает отрицание в окне вокруг ключевой фразы; на это есть отдельный набор тестов с русскими примерами.

## Нормализация

Модуль `normalizer/`: регистр, Unicode NFKC, очистка HTML, пробелы, дефисы, ё→е, похожие символы (латиница/кириллица), словоформы (pymorphy3 или стеммер, обосновать выбор). Матчинг только по нормализованному тексту. `raw_text` хранится отдельно и не изменяется. Синонимы (удалёнка/remote, ИИ/AI/нейросеть) — в конфиге.

## Зарплата

Модуль `salary_parser/`. Типы: MONTHLY, HOURLY, DAILY, WEEKLY, PROJECT, PER_ITEM, FIXED, UNKNOWN, NEGOTIABLE. Валюта неопределима → `UNKNOWN`, не угадывать. Нет зарплаты → `salary_status = NOT_SPECIFIED`. Не сравнивать разные единицы (₽/месяц и ₽ за статью) и не выдумывать месячный доход. Форматы: `30к`, `30 K`, `30 000`, `30.000`, `от/до`, диапазоны с разными тире.

## Дедупликация

Уровни по возрастанию цены: `(source_instance_id, external_id)` → URL → `content_hash` → `normalized_hash` → near-duplicate (simhash или pg_trgm, **только среди кандидатов**, отобранных по индексу/окну по времени; никакого полного попарного сравнения). Одна вакансия из нескольких источников = одна `vacancy` + несколько `vacancy_sources`.

## Идемпотентность

- Уникальные ключи в БД, а не проверки в коде: `(source_instance_id, external_id)`, `(vacancy_id, user_id)` для evaluations и notifications.
- Повторный запуск любого шага не создаёт дубликатов и не шлёт повторных уведомлений.
- Захват задач и уведомлений через `FOR UPDATE SKIP LOCKED` + статус + lease/timeout для зависших.

## Режимы и уведомления

Режимы: `LIVE_MONITORING`, `INITIAL_SYNC`, `BACKFILL`. Исторический импорт **никогда** не создаёт уведомления автоматически (в лучшем случае один дайджест по явной команде). Импорт идёт батчами с checkpoint и возобновляется после остановки.

Notifier соблюдает: `max_notifications_per_minute/hour`, retries с backoff, FloodWait, quiet hours (политики QUEUE_AND_SEND_LATER / SKIP / DIGEST), timezone. Кнопки «Подходит / Не подходит / Скрыть источник» пишут обратную связь в БД.

## Telegram-мониторинг

- Bot API не читает произвольные каналы. Мониторинг — Telethon, интерфейс — aiogram.
- Telethon-сессия работает под **отдельным, не основным аккаунтом**. Это юзербот: есть лимиты подписок, FloodWait и риск бана.
- Опрос каналов разносится по времени (stagger + jitter), с ограничением конкурентности. Один канал не блокирует остальные.
- Не обходить CAPTCHA, авторизацию, paywall, rate limits, антибот-защиту. Недоступный источник получает статус `UNSUPPORTED` или `AUTH_REQUIRED`.

## Сайты-источники (HH, Kwork, FL, Workzilla)

У тебя может не быть доступа к интернету. **Не выдумывай API, эндпоинты и селекторы.** Пока документация не предоставлена в `docs/sources/<name>.md` или в промпте, adapter — заглушка, бросающая `SourceNotSupportedError`, источник получает статус `UNSUPPORTED`. Интерфейс `BaseSourceAdapter` и registry делаются сразу, чтобы добавление adapter не трогало ядро.

Экземпляры источников создаются командой бота (`/add_source telegram @x`, `/add_source hh <url>`) без изменения Python-кода.

## Поиск

`/search` ищет только по данным в PostgreSQL: FTS с русской конфигурацией + `pg_trgm`. Никогда не запускает внешний парсинг. Сортировка: relevance, затем published_at.

## Тесты

- Unit: normalizer, salary, keywords (включая негации), hard/soft/positive, scoring, risk, freshness, dedup, переходы статусов, форматирование сообщений.
- Integration: реальный PostgreSQL (не SQLite). DSN берётся из `TEST_DATABASE_URL`; если не задан — поднимать через testcontainers; если недоступно ни то, ни другое — тесты помечаются skip с понятным сообщением, а не подменяются SQLite.
- Никаких реальных сетевых запросов в тестах. Фикстуры и моки.
- Перед завершением любой задачи: `ruff`, `mypy` (по возможности), `pytest`. Не заявляй «работает», если тесты не запускались; скажи, что именно не удалось запустить.

## Логи и секреты

Уровни DEBUG–CRITICAL. Логировать: run источника, fetched/parsed/duplicates/hard_rejects/approved/sent, ошибки, время. Токены и секреты в логи не писать. Секреты только в `.env`, всегда есть `.env.example`.

## Процесс работы

- Работай малыми законченными кусками. Не переходи к следующей фазе, пока текущая не работает и не покрыта тестами.
- Никаких `TODO`/`pass`-заглушек в заявленном как готовое коде. Если чего-то нет, скажи об этом явно.
- Архитектурные решения кратко фиксируй в `docs/decisions.md` (что и почему).
- Если требования противоречат друг другу, сначала спроси/укажи, потом делай.

## Definition of done для любого куска

1. Код запускается, миграции применяются на чистой БД.
2. Тесты куска написаны и проходят (или явно указано, что не удалось запустить и почему).
3. Идемпотентность проверена тестом повторного запуска.
4. Документация/`docs/` обновлены.
5. Список того, что сознательно не сделано.

## Фазы

0. Вертикальный срез: 1 канал → normalize → 1 hard reject → score → БД → 1 уведомление.
1. Ядро: БД и модели → normalizer + salary → filters + scoring + risk → notification queue + quiet hours → bot + settings.
2. HH.ru (только при наличии документации).
3. Kwork / FL / Workzilla.
4. Масштабирование (отдельные workers, Redis только при доказанной необходимости).
5. Advanced: similarity, аналитика, улучшенный risk.

Фаза 5 не начинается, пока фазы 0–1 не стабильны.
