# Архитектурные решения

Формат: решение → почему → от чего отказались.

## D1. PostgreSQL — единственное хранилище и единственная очередь
Почему: нагрузка — тысячи задач в час, а не десятки тысяч в секунду; `SELECT … FOR UPDATE SKIP LOCKED` даёт атомарный захват, транзакции с данными (checkpoint + вставка одной транзакцией) и переживает рестарт. Меньше движущихся частей.
Отказались от: Redis/RQ/Celery/Kafka. Пересмотр в Phase 4 при замеренном узком месте.

## D2. Один процесс на MVP, модули с чёткими границами
Почему: один пользователь, одна Telethon-сессия (её всё равно использует ровно один процесс). Разделение позже = запуск тех же модулей отдельными точками входа.
Отказались от: сразу 4 контейнеров.

## D3. Наблюдение (`vacancy_sources`) сохраняется до dedup
Почему: падение воркера не теряет данные; ТЗ требует хранить всё; `vacancy_id` nullable → dedup привязывает позже. Состояние pipeline выводится из данных (`PENDING`, `analyzed_at IS NULL`), поэтому восстановление после сбоя = обычный запрос.
Отказались от: PERSIST в конце pipeline (как в ТЗ).

## D4. Extraction и risk — на уровне вакансии, фильтры и score — на паре вакансия × пользователь
Почему: extraction зависит только от текста, а фильтры и score — от настроек пользователя. Считать extraction один раз дешевле и снимает противоречие «hard filters нужен extraction».
Отказались от: порядка hard filters → extraction из ТЗ.

## D5. Три оси статусов
`vacancy_sources.ingest_status`, `vacancy_evaluations.decision`, `notifications.status`. Переходы — явный словарь + исключение на недопустимый. `ingest_status` живёт на наблюдении, а не на вакансии (следствие D3).

## D6. Доставка уведомлений at-most-once
Почему: Telegram `send_message` не идемпотентен; окно «отправили, но не записали» нельзя закрыть без внешней идемпотентности. Редкая потеря (статус `UNCONFIRMED`, вакансия доступна через `/recent`) лучше дубля.

## D7. Поллинг Telethon, а не подписка на updates
Почему: при ~1000 каналов updates могут теряться, catch-up всё равно нужен; поллинг с `min_id` даёт детерминированный checkpoint и единый rate limiter.

## D8. SimHash с полосами для near-duplicate
Почему: отбор кандидатов по индексируемым полосам (4×16 бит) + окно по времени → без O(n²). `pg_trgm` оставлен для поиска, не для dedup.

## D9. Веса и правила — в конфиге/БД, формула с капами по группам
Почему: пользовательские критерии не должны требовать правки кода; капы не дают 10 совпавших слов раздувать score.

## D10. Бот отвечает только владельцу
Почему: бот управляет источниками и настройками; без allowlist любой нашедший бота мог бы менять их.
